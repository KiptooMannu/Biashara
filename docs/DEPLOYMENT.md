# Deploying the BIASHARA API

The backend ships as a container. Everything below assumes the repository root
is what you push to GitHub, with the API under `backend/`.

---

## What was added

| File | Purpose |
|---|---|
| `backend/Dockerfile` | Two-stage build — Maven/JDK 21 builds, JRE 21 runs |
| `backend/.dockerignore` | Keeps `target/`, logs and IDE files out of the build context |
| `render.yaml` | Render Blueprint — service, health check and environment |

And four changes to the application, each one a thing that would have broken in
a hosted environment:

- **`server.port: ${PORT:8080}`** — Render assigns the port and routes to it.
  A service that hard-codes 8080 is marked unhealthy and killed.
- **`spring-boot-starter-actuator`** — gives a real `/actuator/health` for the
  platform to poll. The path was already permitted in `SecurityConfig`; there
  was simply nothing serving it.
- **`forward-headers-strategy: framework`** — TLS terminates at Render's proxy,
  so without this the app sees plain `http` and the wrong host.
- **CORS moved to configuration** — `biashara.cors.allowed-origins`, set with
  `BIASHARA_CORS_ORIGINS`. It was compiled in as `localhost` only, which is
  correct for the Vite proxy in development and blocks every call once the
  frontend is on its own domain.

## Build and run locally

From `backend/`:

```bash
docker build -t biashara-api .

docker run --rm -p 8080:8080 \
  -e BIASHARA_DB_URL="jdbc:postgresql://<host>/neondb?sslmode=require&prepareThreshold=0" \
  -e BIASHARA_DB_USER="<user>" \
  -e BIASHARA_DB_PASSWORD="<password>" \
  -e BIASHARA_JWT_SECRET="<64+ random characters>" \
  -e BIASHARA_CORS_ORIGINS="http://localhost:5173" \
  biashara-api
```

Then check:

```bash
curl http://localhost:8080/actuator/health      # {"status":"UP"}
curl http://localhost:8080/api/auth/demo-accounts
```

The first build takes several minutes — it resolves the full dependency tree.
Later builds reuse that layer unless `pom.xml` changes.

Omitting the environment variables entirely still works: every value falls back
to the committed demo default. That is deliberate for the local demo and wrong
for anything public.

## Deploy to Render

### 1. Push to GitHub

This directory is not a git repository yet:

```bash
git init
git add .
git commit -m "BIASHARA"
git remote add origin git@github.com:<you>/biashara.git
git push -u origin main
```

`.gitignore` already excludes `target/` and `node_modules/`.

### 2. Create the service

**Dashboard → New → Blueprint**, select the repository. Render reads
`render.yaml` and proposes one web service. Or create it by hand:

| Field | Value |
|---|---|
| Runtime | Docker |
| Root directory | `backend` |
| Dockerfile path | `./Dockerfile` |
| Health check path | `/actuator/health` |
| Instance type | Free is enough to demo; 512 MB |

### 3. Set the environment variables

Render prompts for the four marked `sync: false`:

| Key | Value |
|---|---|
| `BIASHARA_DB_URL` | `jdbc:postgresql://ep-….neon.tech/neondb?sslmode=require&prepareThreshold=0` |
| `BIASHARA_DB_USER` | Neon role |
| `BIASHARA_DB_PASSWORD` | Neon password — **rotate the committed one first** |
| `BIASHARA_CORS_ORIGINS` | `https://<your-frontend>.onrender.com` |

`BIASHARA_JWT_SECRET` is generated by Render. `SPRING_PROFILES_ACTIVE`,
`BIASHARA_SEED_ENABLED` and `JAVA_OPTS` come from the blueprint.

Keep `prepareThreshold=0` on the URL. Neon's pooler multiplexes clients onto
shared server connections and caches statement plans against them, so without
it a schema change raises *"cached plan must not change result type"*.

### 4. First boot

The seeder is idempotent and keys off the tenant slug, so pointing at an
already-seeded Neon database costs one pass of row counting rather than a
rebuild. Watch the logs for:

```
All 27 tables have at least 10 rows.
```

Then set `BIASHARA_SEED_ENABLED=false` so restarts skip the check entirely.

## The frontend

Not covered by this container. It is a Vite static build, and it currently
calls `/api` on its own origin through the dev-server proxy — which does not
exist in production. Two options:

- **Static site + rewrite (simplest).** Deploy `frontend/` as a Render static
  site with build `npm ci && npm run build`, publish `dist`, and add a rewrite
  rule from `/api/*` to `https://biashara-api.onrender.com/api/*`. The browser
  keeps seeing one origin and CORS never comes up.
- **Separate origins.** Point axios at the API host and make sure that origin
  is listed in `BIASHARA_CORS_ORIGINS`.

Either way, add a SPA rewrite from `/*` to `/index.html`, or a refresh on
`/dashboard` returns 404.

## Notes on the free tier

- **Cold starts compound.** Render free instances sleep after 15 minutes and
  Neon scales to zero independently. The first request after a quiet period can
  take the better part of a minute while both wake. Load one page before
  presenting.
- **512 MB.** `JAVA_OPTS` uses `MaxRAMPercentage` rather than a fixed `-Xmx`, so
  the JVM reads the container limit and the same image is correct on a larger
  instance without a change.
- **`ddl-auto: update`** is still how the schema is managed. It is right for a
  demo and wrong for production — a real deployment wants versioned migrations
  before a second person can deploy.
